# Tasks: the desk sees the floor

**Input**: Design documents from `/specs/001-the-desk-sees-the-floor/`

**Prerequisites**: plan.md (required), spec.md (required for user stories), data-model.md, contracts/floor-document.md

**Tests**: Required. Constitution IV makes every acceptance scenario a committed test one of the four `ergane.yaml` gates runs headless, so test tasks appear in every phase and cite the scenario they prove. A task that renders anything the operator sees also cites the `DESIGN.md` section it implements (constitution VIII).

**Organization**: Tasks are grouped by user story. Ergane hands each node exactly the section whose heading names its story; there is no Setup or Foundational phase — shared groundwork sits inside the phase of the story that needs it first, and every later story branches from `dev` after that story has **merged** (`depends_on_merged`, spec `## Work Graph`).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (e.g., US1, US2, US3, US4)
- Include exact file paths in descriptions
- `(spec USn-Sk)` names the acceptance scenario the task exists to prove; `(DESIGN.md § …)` names the section a rendering task implements

## Path Conventions

Two package worlds in one repository (plan.md, Structure Decision): the backend is
the `pane/` package with `tests/` beside it, both owned by `uv` from
`pyproject.toml` at the repository root; the frontend is `web/` (`web/src`,
`web/tests/unit`, `web/tests/smoke`), owned by `npm`. Fixtures are `fixtures/` at
the root and are **read, never written** by any task below. Every command runs
from the repository root unless the path says otherwise.

## Dependencies & Execution Order

### Phase Dependencies

- **User Story 1 (Phase 1)**: no dependencies. Carries both package worlds, the
  gate wiring, the tokens, and the masthead because every later story's tests run
  under the gates it creates.
- **User Story 2 (Phase 2)**: waits on Phase 1 having **merged** into `dev`
  (`depends_on_merged`), because its loader, assembly, and tests live in the
  package and test directories Phase 1 creates.
- **User Story 3 (Phase 3)**: waits on Phase 2's merge: its endpoints are tested
  by replaying Phase 2's fixtures, and it edits `pane/readers.py`,
  `pane/floor_document.py`, and `pane/app.py` in place.
- **User Story 4 (Phase 4)**: waits on Phase 3's merge: its smoke drives Phase 3's
  backend in demo mode and its consumer imports Phase 3's `events.ts` and types.

copy Ergane compiles. Change one and change the other.

  tokens and styles, then the page, then tests, then the clean-checkout proof.

  the room → unit proofs → Playwright config → smokes → the clean-checkout run.

## Notes

- `[P]` tasks = different files, no dependencies
- `[Story]` labels map tasks to user stories for traceability, and to a dispatched agent: a task tagged for no story is work no agent is given
- `(spec USn-Sk)` cites the acceptance scenario a task exists to satisfy. A task may only cite a scenario of the story whose phase it sits in — a citation across stories reads as work filed under the wrong agent
- No task under Phase 2 creates, edits, or renames a payload or envelope under `fixtures/`; only `fixtures/README.md` changes, and only in Phase 2
- The tasks most likely to be silently wrong: **T024/T035** (a defaulted field that becomes `0` instead of `None`), **T036** (a route added outside the guarded router — FastAPI's docs routes included), **T050** (the paged-while-verifying node collapsed into `WAITING_OPERATOR`), and **T062** (a request listener registered after navigation, which would miss the document request). The cited tests exist to catch exactly those
- Commit after each task or logical group; one story per PR; the PR title names the story so `ergane spec landed` can read it
